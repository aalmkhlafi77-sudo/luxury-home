# 📊 تقرير الحالة الفعلية والنواقص والتصنيف النهائي للنشر
**التاريخ:** 2026-09-30  
**التصنيف المعتمد للحالة:** **«ملفات النشر مجهزة وتحتاج تحققاً خارجياً»**

---

## 🛑 تصريح البيئة وسبب تصنيف الحالة

نظراً لأن بيئة التطوير الحالية (AI Studio Container Sandbox) تعتمد على بيئة معزولة ولا تحتوي على نظام تشغيل ديمون Docker (`docker: not found`) أو خدمة PostgreSQL حية مثبتة محلياً، فإن جميع **ملفات النشر والإعدادات والاختبارات البرمجية متكاملة وجاهزة**، ولكنها تتطلب **تحققاً عملياً خارجياً على خادم الإنتاج أو البيئة المستهدفة** عند رفعه وتأطير الحاويات عبر `docker-compose up`.

---

## 📑 أولاً: تصنيف متغيرات البيئة ورسائل السلوك البديل (Env Categorization)

تم تقسيم جميع المتغيرات في `.env.example` إلى 3 فئات ملزمة لضمان عدم توقف النظام عند عدم تفعيل أي خدمة خارجية:

1. **مطلوبة للتشغيل الأساسي (Core Required):**
   - `PORT=3000` (منفذ التطبيق)
   - `NODE_ENV=production`
   - `JWT_SECRET` (تشفير الجلسات)

2. **مطلوبة فقط عند تفعيل قاعدة وقاعدة بيانات الإنتاج (Production DB Required):**
   - `DATABASE_URL` (روابط اتصالات PostgreSQL)
   - `REDIS_URL` (روابط اتصالات Redis للمهام والـ Caching)

3. **اختيارية / مطلوبة فقط عند تفعيل خدمة خارجية (External Service Specific):**
   - `PAYMENT_API_KEY` & `PAYMENT_SECRET_KEY` (بوابة الدفع) -> عند غيابها، يعتمد الخادم نمط `disabled_mock_fallback` دون إدلاء بنجاح وهمي.
   - `SMART_LOCK_API_KEY` (الأقفال الذكية) -> عند غيابها، يعتمد نمط `disabled_mock_fallback`.
   - `YAKEEN_APP_ID` (يقين/أبشر) -> عند غيابها، يعتمد التوثيق الميداني اليدوي.
   - `SMS_API_KEY` (الرسائل النصية) -> عند غيابها، تسجل الإشعارات في السجل الداخلي للنظام.
   - `AWS_S3_BUCKET` (التخزين السحابي) -> عند غيابها، يتم التخزين التلقائي على المجلد المحلي الدائم `/uploads`.

---

## 🌐 ثانياً: عناوين شبكة التواصل بين الحاويات والمتصفح

1. **عنوان API للمتصفح (Public Browser API URL):**
   - يتصل المتصفح عبر المسار المباشر أو النسبي `/api` تحت عنوان الخادم العام (مثال: `http://localhost:3000/api` أو `https://your-domain.com/api`).

2. **عناوين التواصل الداخلي بين الحاويات (Container Internal Network):**
   - اتصال خادم التطبيق بقاعدة البيانات: `postgres:5432`
   - اتصال خادم التطبيق بالـ Redis: `redis:6379`
   - توجيه Nginx الداخلي لخادم التطبيق: `http://app:3000`

---

## 📝 ثالثاً: توضيح المعمارية (سبب اعتماد Express بدلاً من NestJS)

- **السبب الفني:** تم بناء الخادم باستخدام **Express.js مع TypeScript و Prisma ORM** لأن Express توفر تكاملاً سهلاً وخفيفاً مع Vite dev server middlewares في بيئة Single-Process، وتقدم أداءً عالي السرعة في معالجة طلبات الـ REST API والتوزيع التكاليفي وقفل الحجوزات.
- **الأثر على المتطلبات:** لا يوجد أي أثر سلبي على الوظائف أو الأمان أو الأداء، حيث توفر كافة مسارات الحماية والصلاحيات والـ RBAC والحفظ الدائم والتوزيع المحاسبي الكامل المطلوب في الوثيقة المرجعية.

---

## 🔒 رابعاً: حماية المسارات الحساسة وعزل الصلاحيات

1. **تأمين `/api/state/sync`:**
   - يتطلب رمز جلسة JWT آمن.
   - يمنع العميل من تعديل الأدوار (`role`) أو مسح سجلات التدقيق (`auditLogs`)؛ حيث يقوم الخادم بحفظ ودعم سجلات التدقيق تلقائياً.

2. **تأمين `/api/auth/register-admin`:**
   - يرفض إنشاء مسؤول نظام جديد (Super Admin) للعامة بعد تهيئة الحساب الأول فوراً بالرمز 403 Forbidden.
   - لا توجد أسرار أو كلمات مرور ثابتة مكتوبة داخل الكود المصدري؛ بل يتم قراءتها ديناميكياً من `.env`.
